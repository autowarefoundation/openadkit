# Container images staged onto the board by scripts/stage-container-images.sh.
#
#   <load-ref>  <pull-ref>@<arm64-digest>
#
# <load-ref>  the reference the board will carry after `podman load`, and the
#             exact string awf-oak-x5h.env names in AUTOWARE_IMAGE /
#             SCENARIO_SIMULATOR_IMAGE. These two MUST agree: every unit sets
#             Pull=never, so a mismatch is an immediate "image not known"
#             start failure rather than a pull.
# <pull-ref>  what skopeo reads the bytes from, addressed by digest so the
#             transfer is reproducible.
#
# WHY THE LOAD REF IS THE FULL REGISTRY NAME and not localhost/<name>:latest,
# which is what this file's retired six entries used. Three reasons, in order
# of weight:
#
#   1. The env file and the five unit files already name these images by
#      their registry references, and the board already carries them under
#      exactly those names (loaded that way during the image survey, before
#      this file was repinned). Retagging to localhost/ would mean editing
#      the env file in lockstep and re-staging 12 GB to rename what is
#      already there.
#   2. `podman images` on the board then shows where the bytes came from.
#      With localhost/<name>:latest, provenance lives only in this file, and
#      the board cannot be audited on its own.
#   3. Pull=never is what makes a real registry reference safe: a store miss
#      fails immediately instead of starting a 5 GB pull from the board.
#
# The one image that is NOT here: BRIDGE_IMAGE (localhost/openadkit-bridge:latest).
# It has no registry reference at all -- it is built on the board from
# components/bridge/Dockerfile -- so this script cannot stage it, and its
# localhost/ name is correct for that reason rather than by the convention
# above.
#
# REPRODUCING A DIGEST BY HAND. Use this form, which works for both manifest
# shapes:
#
#   skopeo inspect --override-arch arm64 --override-os linux \
#     --format '{{.Digest}}' "docker://<ref>"
#
# This file used to document a `jq '.manifests[] | select(.platform...)'`
# recipe against `skopeo inspect --raw`. That form reads a manifest LIST (an
# OCI index or a Docker manifest list) and picks the arm64 member out of it.
# Both refs below are single-arch manifests -- `skopeo inspect --raw` returns
# application/vnd.docker.distribution.manifest.v2+json with no `.manifests`
# key at all -- so the jq recipe returns nothing for them, silently, which
# reads as "no arm64 build" rather than as "wrong recipe". The
# --override-arch form above returns the right digest for a manifest list too
# (it resolves the list and reports the selected member), so there is one
# recipe rather than two. To tell which shape a ref has:
#
#   skopeo inspect --raw "docker://<ref>" | jq -r '.mediaType'
#
# skopeo needs XDG_RUNTIME_DIR set (export XDG_RUNTIME_DIR=/run/user/$(id -u));
# without it it fails while looking for auth.json and reports something that
# looks like an authentication or network problem instead.
#
# THE DIGEST ON THE BOARD WILL NOT MATCH THE DIGEST BELOW, and the pin has not
# drifted. `skopeo copy` into an oci-archive: destination rewrites a Docker
# schema-2 manifest into OCI media types, which changes the config blob and
# therefore the manifest digest. Measured 2026-08-18: registry
# sha256:d161659c… loads onto the board as sha256:11f418e1… . Do NOT write a
# verification step that compares `podman images --digests` against this file
# -- it reports a false mismatch on a correctly staged board. Content identity
# was verified instead through the layer diff_ids, which survive the format
# conversion; all 27 matched for universe-after:
#
#   ssh root@<board> "podman image inspect <ref> \
#     --format '{{range .RootFS.Layers}}{{.}}{{\"\n\"}}{{end}}'"
#   skopeo inspect --config --override-arch arm64 --override-os linux \
#     "docker://<ref>" | jq -r '.rootfs.diff_ids[]'
#
# Digests below re-verified against the registry on 2026-08-19.
#
